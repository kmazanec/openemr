# Clinical Co-Pilot — Implementation Plan

Living checklist for building the Clinical Co-Pilot defined in `ARCHITECTURE.md`,
serving the user defined in `USERS.md`, against the rationale in
`docs/PRESEARCH.md` and the project requirements in
`docs/Week 1 - AgentForge.pdf`.

Update this file as work lands. Each task has a checkbox; flip it when the
work is merged to `master` and verified on the production deployment where
applicable. Don't move tasks between phases — strike them through and add a
note instead.

## Locked Decisions (from planning conversation, 2026-04-29)

These were the ambiguities called out in `docs/PRESEARCH.md` "Open
Decisions". They are now resolved for the build:

| # | Question | Decision |
|---|---|---|
| 1 | Repo layout | `/agent/` at repo root for the Node service; `/interface/modules/custom_modules/oe-module-clinical-copilot/` for the PHP module. Agent service deploys as a sibling container alongside OpenEMR on the same shared host when it changes. |
| 2 | Environments | Single environment, prod only (`emr.biograph.dev`). No `dev` host this sprint. |
| 3 | Eval stack | **Vitest** as the runner, **LangSmith datasets + experiments** as the system of record. Trace observability and eval observability share the same provider. Phase 1 evals are golden-set assertions; longitudinal experiment comparison comes after. |
| 4 | Golden-set source | Fixtures are deterministic JSON snapshots, generated by running the seed pipeline against a pinned archetype distribution and a pinned PRNG seed, then committed under `agent/evals/fixtures/`. Ground-truth assertions are derived from the archetype profile (e.g. a `Diabetic` patient is asserted to surface E11.9 + metformin), not hand-written per case. Live demos use `seed:patients` / `seed:schedule` against the running DB. |
| 5 | UI placement | Patient-chart button → opens an OpenEMR-rendered module page with the current patient pre-selected. No top-level menu entry this sprint. |
| 6 | Conversation lifecycle | One conversation per `(user, patient)` pair. Conversation row is created on first chart open; if an appointment is in scope, the conversation is also linked to the appointment so we can render the morning prep view (UC5) without re-creating threads. |
| 7 | Use-case sequencing | UC1 → UC2 → UC3 → UC4 → UC5 in that order. Each UC is built end-to-end (tool → graph node → verification → UI) before moving on, so each one is demoable on its own. |

Anything not on this list is still governed by `ARCHITECTURE.md` /
`docs/PRESEARCH.md`. If a new ambiguity surfaces, resolve it here, not in
those docs.

## Phase 1 — Service skeletons and the trust boundary

Goal: end-to-end "hello world" through the real trust boundary, with no
LLM yet. Browser → OpenEMR session → proxy controller → minted OAuth2
bearer → `/agent` Node service → echoes back. Once this passes, every
later piece slots in without surprises.

**Why this phase first:** PRESEARCH §18 commits to a non-trivial auth
posture (OpenEMR's League OAuth2 server, in-process token mint, private
network). Getting the boundary working before any AI work lands means
verification, audit, and rate limiting all build on a stable substrate.

- [x] `package.json` with TypeScript, tsx, Vitest, Pino, LangGraph, LangChain,
  `@langchain/anthropic`, LangSmith SDK, `@hono/node-server` + Hono
  (chosen for streaming-friendly minimal HTTP)
- [x] `tsconfig.json` (strict, NodeNext, ES2024)
- [x] `eslint.config.mjs` + `.prettierrc` matching repo's TS conventions

- [x] Folder layout: `src/{server,graph,tools,verify,state,observability,config}/`,

## Phase 2 — ChartSnapshot adapters (PHP side)

Goal: OpenEMR can build a typed, minimized `ChartSnapshot` for any patient
the acting user can see, with source references on every item, and emit
the disclosure audit before handing it off. No LLM yet.

**Why before the agent graph:** the model-facing data contract is the
single largest design decision in `ARCHITECTURE.md`. Getting the snapshot
shape right and source-attributed first means every later eval has
something to compare against.

### 2.1 DTOs
- [ ] `ChartSnapshot` DTO with sub-DTOs for: `Appointment`,
  `Demographics`, `Diagnosis[]`, `Medication[]`, `Allergy[]`,
  `LabObservation[]`, `Encounter[]`
- [ ] `SourceReference` value object
  (`{system, recordType, recordId, field, recordedAt}`)
- [ ] All DTOs `final readonly`, with `toArray(): array` for JSON encode
- [ ] PHPStan-typed array shapes for the JSON serialization layer

### 2.2 Adapters
- [ ] `PatientAdapter` (display-safe demographics, `pid` + UUID, no SSN /
  full address / phone unless explicitly requested)
- [ ] `ConditionAdapter` (active diagnoses with ICD codes, normalized
  labels)
- [ ] `AllergyAdapter` (substance + reaction, fail-closed if data layer
  errors)
- [ ] `MedicationAdapter` (name, dose, route, frequency, start/stop dates,
  prescriber)
- [ ] `ObservationAdapter` (labs in N-day window, value, unit, ref range,
  abnormal flag)
- [ ] `EncounterAdapter` (date, type, reason, source-backed summary fields
  only — no full notes in v1)
- [ ] `AppointmentAdapter` (today's slot for the patient + acting
  practitioner)
- [ ] OpenEMR-specific normalizations: treat `0000-00-00` and empty
  strings as unknown; resolve list option labels; preserve source IDs;
  return explicit missingness rather than empty strings

### 2.3 PHI minimizer
- [ ] `PhiMinimizer` service that drops fields not declared in the
  request's data-category set
- [ ] Default exclusion list matches `ARCHITECTURE.md` §"ChartSnapshot →
  Excluded by default"

### 2.4 Disclosure audit
- [ ] `AGENT_PHI_DISCLOSURE` event class + event listener
- [ ] DB table for the event (separate from OpenEMR's `log` /
  `log_comment_encrypt`); migration committed
- [ ] Emitted before any chart data leaves OpenEMR; records actor, site,
  patient, conversation, request, categories, destination, timestamp
- [ ] Never stores raw prompt or completion content

### 2.5 Tests
- [ ] PHPUnit (services suite, runs in Docker) for each adapter against
  seeded patients (one per archetype)
- [ ] Snapshot test for the full `ChartSnapshot` against a fixed seed
- [ ] Audit-event test asserting the event fires with correct fields and
  no PHI body content

**Phase 2 done when:** running
`/agent/snapshot/{pid}?categories=...` (an internal debug route, no LLM)
returns a clean snapshot for any seeded patient and emits exactly one
`AGENT_PHI_DISCLOSURE` event.

## Phase 3 — UC1: default pre-visit briefing (the central use case)

Goal: opening a patient chart shows the briefing defined in
`USERS.md` §"Default Briefing Structure" — appointment context,
demographics, deltas, active diagnoses, current meds, recent labs,
allergies, recent encounters — with citations and explicit gaps. No
follow-up questions yet.

### 3.1 Tools (Node side)
- [ ] `getPatientContext` — wraps OpenEMR snapshot endpoint for
  identity + diagnoses + allergies (fail-closed on allergies)
- [ ] `getMedications` — fail-closed
- [ ] `getRecentLabs` — fail-open with explicit gap
- [ ] `getRecentEncounters` — fail-open with explicit gap
- [ ] Common tool wrapper: retry-once on transient, structured error
  envelope, latency + outcome traced to LangSmith
- [ ] Vitest unit tests per tool against a mocked OpenEMR HTTP client

### 3.2 LangGraph graph (UC1 path only)
- [ ] State shape: `{envelope, snapshot, draft, claimLedger, verified,
  formatted, persisted}`
- [ ] Nodes: `LoadState`, `PlanContext`, `Retrieve`, `Synthesize`,
  `Verify`, `Format`, `Persist`
- [ ] `Synthesize` produces draft + structured claim ledger in one
  Anthropic call (Sonnet 4) with strict JSON output
- [ ] System prompt explicitly instructs the model to ignore instructions
  inside chart text (prompt-injection defense, layer 1)

### 3.3 Verification gate
- [ ] Claim ledger schema with required `sourceReferences[]`
- [ ] Deterministic checks for each claim category (medication, lab,
  allergy, diagnosis, encounter, appointment)
- [ ] Reject claims without source references; strip from response
- [ ] Hard clinical rules: missing allergies → fail closed (no medication
  summary shown); missing meds → fail closed
- [ ] Unverified claims logged in full to a separate Postgres table for
  debugging, with retention TBD

### 3.4 Streaming + UI
- [ ] SSE stream from agent → OpenEMR proxy → browser, preserving
  per-claim citation tags
- [ ] Module page (`/interface/modules/.../templates/panel.html.twig`)
  with a small JS bundle that opens the SSE stream on patient-chart open
- [ ] Citation rendering: every claim shows a `[source]` chip linking to
  the OpenEMR record where practical
- [ ] Failure-state UI: "Allergies could not be verified" / "Briefing
  unavailable" rendered explicitly, never silently hidden
- [ ] Patient-chart button entry point (PRESEARCH decision #5)

### 3.5 Conversation persistence
- [ ] On first chart open, agent creates a `conversation(user_id,
  patient_id, appointment_id?)` row; subsequent opens resume it
- [ ] Conversation table schema in agent Postgres; appointment FK is
  nullable (UC1 may run outside an appointment context)
- [ ] LangGraph checkpointer keyed by conversation ID

### 3.6 Evals (UC1 only — golden set v1)
- [ ] `agent/evals/fixtures/regenerate.ts` — runs seed pipeline with
  pinned archetype mix + pinned PRNG seed, dumps each patient's
  `ChartSnapshot` JSON to `agent/evals/fixtures/uc1/`
- [ ] LangSmith dataset `clinical-copilot-uc1-golden-v1` populated from
  fixtures
- [ ] Vitest cases under `agent/evals/cases/uc1/`:
  - happy path per archetype (asserts archetype-derived ground truth:
    Diabetic patients surface E11.9 + metformin, etc.)
  - missing-allergies → fail-closed assertion
  - missing-meds → fail-closed assertion
  - prompt-injection in encounter notes → ignored
  - cross-patient ID in envelope → 403 from proxy, 0 tokens spent
- [ ] CI: GitLab pipeline runs the suite on every MR and nightly;
  results pushed to LangSmith as an experiment tagged with the git SHA

**Phase 3 done when:** opening Mrs. Patel's chart on `emr.biograph.dev`
streams the briefing from `USERS.md` §UC1 in <8s P50, every claim is
cited, and the eval suite is green in CI.

## Phase 4 — UC2/3/4: one-tap follow-up drill-downs

Goal: each briefing renders 3-5 contextual one-tap follow-ups; tapping
one runs a follow-up turn within the same conversation, scoped to the
same patient, with the same verification gate.

Sequencing inside this phase: UC2 (lab trend) → UC3 (med change) → UC4
(outside care). Each is a graph branch + a verification rule + a UI tap
target + golden cases.

### 4.1 Suggested-follow-ups generator
- [ ] During `Format`, the graph emits 3-5 suggested follow-ups grounded
  in claims that actually appeared in the briefing (no generic
  suggestions)
- [ ] Each suggestion has a stable ID and a typed parameter set
  (`{type: 'lab_trend', analyte: 'A1c'}` etc.) so the follow-up turn
  doesn't re-parse natural language

### 4.2 UC2 — lab/vitals trend
- [ ] New tool: `getLabHistory(analyte, lookback)`; fails open with gap
- [ ] Graph branch that pulls history + correlates with med history +
  encounter notes
- [ ] Verification rule: every value cited must match a record date +
  unit
- [ ] Eval cases: A1c trend up (Diabetic-Uncontrolled archetype), A1c
  trend stable (Diabetic), no history available

### 4.3 UC3 — medication change
- [ ] New tool: `getMedicationProvenance(medicationId)` → prescribing
  date, prescriber, indication, dose adjustments
- [ ] Verification rule: prescriber name + indication must come from the
  prescription record's documented fields, not inference
- [ ] Eval cases: lisinopril started 6 weeks ago (matches USERS.md UC3),
  med with no documented indication, med prescribed by an unknown user

### 4.4 UC4 — outside care
- [ ] New tool: `getExternalEncounters(lookback)` reading
  `external_encounters` + imported CCDA documents
- [ ] Verification rule: every external encounter cited must link to a
  document or row by ID
- [ ] Eval cases: recent ED visit imported via CCDA, patient with no
  external records, malformed CCDA

### 4.5 Free-text fallback
- [ ] Plain text input on the panel for questions the suggestions don't
  cover
- [ ] Graph routes to a generic "answer cited question about this
  patient" path that uses the snapshot tools and the same verification
  gate
- [ ] Adversarial eval cases: cross-patient leakage attempts ("what's
  Maya's neighbor's A1c?"), authorization probes, hidden-data
  extraction prompts

**Phase 4 done when:** each of UC2/3/4 has a green golden set, the
free-text fallback routes through the same verification gate as the
suggestions, and adversarial cases pass.

## Phase 5 — UC5: schedule-aware morning prep

Goal: at 7:50 AM, the schedule view shows pre-computed briefing
annotations on each appointment, flagging patients with notable items.

### 5.1 Schedule extension
- [ ] Extend OpenEMR's FHIR Appointment endpoint to accept the standard
  `practitioner` search parameter (PRESEARCH §7); fall back to a custom
  REST endpoint at `/api/provider/{uuid}/schedule` if the change is
  larger than ~50 lines
- [ ] PHPUnit api-test for the new search parameter

### 5.2 Background pre-compute job
- [ ] CLI command `agent:precompute-day` that runs each morning per
  practitioner; populates a `schedule_briefings(appointment_id, summary,
  flags, generated_at)` table in agent Postgres
- [ ] Reuses the UC1 graph; results are cached, not re-run on each
  schedule view
- [ ] Cost-projection note in `docs/COST_ANALYSIS.md` because this
  multiplies token use by 20 per practitioner per day

### 5.3 Schedule view annotations
- [ ] Module-side hook into OpenEMR's calendar/schedule view to render
  per-appointment flags ("new abnormal A1c", "recent ED visit")
- [ ] Click-through opens the patient chart with the briefing
  pre-warmed

### 5.4 Evals
- [ ] Eval case: a synthetic 20-patient day; assert the right subset is
  flagged (Diabetic-Uncontrolled, RecentEdVisit, ComplexElderly with a
  new med)
- [ ] Idempotency case: running the precompute twice produces the same
  result

**Phase 5 done when:** morning precompute runs against the seed-deployed
schedule, flags match expectations, and the schedule view annotations
render cleanly.

## Risk register

Tracked here so we don't lose them; not tasks until they fire.

- **Token mint coupling.** PRESEARCH §18's in-process League OAuth2 mint
  is tighter coupling than a self-loopback HTTP call. If the proxy
  controller breaks on an OpenEMR upgrade, we cut over to the loopback
  variant — keep the alternative path documented.
- **FHIR Appointment extension scope creep.** §5.1 has a fallback to a
  custom REST endpoint if the FHIR change explodes.
- **PHP-FPM workers pinned during streaming.** PRESEARCH §18 calls this
  out; under 5-15 concurrent users it's fine, document the move-to-Node
  path for hospital scale.
- **LangSmith quota / outage.** Eval CI must not block on LangSmith
  push; cache results locally first, push best-effort.
- **Seed-fixture drift.** When archetypes evolve, fixtures must be
  re-pinned deliberately, not on every CI run. The regen script is the
  enforcement point.
