# Week 2 Pre-Search — Multimodal Evidence Agent

Working document. Captures what's already built (Week 1), what Week 2 demands, and the architectural decisions that need to be made before code lands. Mirrors the Phase 1/2/3 structure of `docs/Pre-Search-Checklist.md` and the pattern of `docs/PRESEARCH.md`.

The companion document for the answers will be `docs/W2_ARCHITECTURE.md` (a new submission deliverable per the PDF). This file is a thinking surface — answer or strike through every open question here, then promote the resolved decisions into the architecture doc.

---

## Week 2 in one paragraph

Week 1's agent reads the structured chart and produces a source-cited briefing. Week 2 adds two capabilities on top:

1. **Multimodal ingestion.** A `attach_and_extract(patient_id, file_path, doc_type)` tool accepts a **lab PDF** and an **intake form** (image or PDF), uses a vision LLM to extract strict-schema JSON with per-field citations (page + bbox), persists the source document in OpenEMR, and writes derived facts as FHIR resources or OpenEMR records — every fact pointing back to the document.
2. **Multi-agent routing.** The Week 1 retrieve→synthesize→verify pipeline is generalized into a **supervisor** that routes work to two workers: an **intake-extractor** (the Week 2 vision/schema worker) and an **evidence-retriever** (a hybrid RAG over a small clinical-guideline corpus, with reranking). The Week 1 verifier remains the gate.

A 50-case golden set with **boolean** rubrics blocks regressions in CI. The hard gate during grading is an injected regression that the eval suite must catch.

## Phase 1 — Constraints (unchanged from Week 1 unless noted)

The Week 1 user (Dr. Patel, primary care, 90-second window) and the verification policy (only source-attributed claims reach the user, hard stops on allergies/meds, verified or not — no probabilistic confidence) carry forward. Domain, scale, reliability, and team constraints are unchanged. The relevant *additions* below.

### W2-1. New use case: ingesting unstructured external evidence

Dr. Patel opens a follow-up chart and the front desk has uploaded a PDF lab report (received by fax) and a scanned intake form (filled out by the patient in the waiting room). The chart's structured data is stale; the recent information lives in those two documents.

**Q1 — RESOLVED.** Target architecture is **(C) Both** — manual in-panel upload for ad-hoc, plus a background sweep that reacts to documents uploaded through OpenEMR's existing front-desk document UI. **Phased delivery: MVP ships (A) manual only; (B) background trigger lands in a later phase.**

**What this commits us to architecturally** — the extractor (`attach_and_extract`) is a single internal capability invokable from either trigger path. Both paths share:
- The same intake-extractor worker, the same strict schemas, the same verifier, the same persistence path, the same citation contract.
- The same idempotency key (a hash over `document_uuid` + extractor version) so a doc that arrives via (A) and is later re-swept by (B) doesn't double-extract or double-write.
- The same disclosure-audit emit (one `AgentDisclosedEvent` per extraction, regardless of trigger).

What differs between trigger paths:
- **Trigger surface.** (A) is a POST from the panel JS to a new `extract` agent route, which streams progress back over SSE alongside the briefing. (B) is a server-side observer (most likely an OpenEMR event listener on document-create, or a CLI sweep on a cron) that calls the same agent endpoint with a system-actor JWT — same trust boundary as `agent:precompute-day` (Phase 5.3 of the W1 plan).
- **User-facing feedback.** (A) shows live progress in the panel. (B) writes results silently; the user notices on next chart open because the briefing now reflects the extracted facts (with a "new since last visit" delta marker — same shape as W1's existing delta rendering).
- **Authorization.** (A) inherits the panel's session and acting-user identity. (B) runs as a system actor and must re-check that the document's pid matches the extraction call's pid (no implicit cross-patient).

**MVP cut line.** Ship (A) only for the demo. The architecture must not foreclose (B) — concretely, the extractor tool must take `(document_uuid, pid, doc_type, trigger_source)` as inputs and not assume it was invoked from a UI session. Trigger source (`'panel'` vs `'autosweep'`) is logged on the trace so we can tell the two paths apart in observability.

**(B) deferred work, captured here so it's not lost:**
- Choose the trigger mechanism: Symfony event listener on `documents.post_insert` (in-process, immediate) vs. a periodic CLI sweep (`agent:autoextract-pending`, cleaner failure isolation). Recommendation when we get there: event listener with a fallback CLI sweep for documents that fail extraction first time.
- Decide which document categories trigger autoextraction (probably "Lab Results" and "Intake Forms" only — not every uploaded document is in scope for the agent).
- Settings page surface (per-practitioner opt-in, mirroring Phase 5.2's morning-prep settings).
- Eval cases that exercise the (B) path through the same fixtures, asserting equivalence with (A).

### W2-2. Document type scope (the hard line on scope creep)

PDF Pitfall #1: "Trying to support five document types before two work reliably." The PDF demands two: **lab PDF** and **intake form**. Stretch is a third (referral fax or medication list).

**Q2 — RESOLVED.** Two document types: `lab_pdf` and `intake_form`. Frozen for W2 — any third type is gated behind both passing all 50 evals.

**Sub-decisions:**

- **Q2a — doc type selection: KEEP.** Lab PDF + intake form is the right cut.
- **Q2b — intake_form demographics scope:** **EXTRACT** name, DOB, sex, address, phone, email, emergency contact. The intake form is the canonical source for "did anything change since last visit" (especially address — patients move and don't tell the front desk). The extractor surfaces deltas; the synthesizer flags them in the briefing ("address on file differs from intake form"); the user/staff decides whether to update the chart. Note that this **diverges from the W1 PHI minimizer's `Demographics` exclusion list** — W1 excludes address/phone/email from the chart snapshot fed to the synthesizer, but the W2 extraction artifact intentionally carries them so the comparison can be made. The minimizer rule still applies to chart-side data going to the model; the intake-form extraction is a separate artifact with its own data category.
- **Q2c — schema strictness: `extra='ignore'`** (Zod `.passthrough()` style — silently drop unknown fields rather than reject the whole extraction). Less brittle on the first pass; the verifier still rejects any *cited* claim whose field isn't in our schema. Trade-off accepted: silent drops mean we don't catch model drift as fast — mitigated by an eval rubric (`schema_complete`) that asserts the LLM populates every expected field, not by strict mode.

**Frozen schemas:**

```
lab_pdf:
  patient: { name, dob }                       # for matching to chart
  collection_date: ISO8601
  lab_facility: string|null
  ordering_provider: string|null
  results: list[{
    test_name: string                          # raw text as printed
    loinc_code: string|null                    # if normalized
    value: string                              # preserve qualifiers like "<0.01"
    unit: string|null
    reference_range: { low, high, text } | null
    abnormal_flag: 'H'|'L'|'HH'|'LL'|null
    citation: { page, bbox: [x,y,w,h], quote }
  }]
  document_citation: { page_count, ocr_quality_estimate }
```

```
intake_form:
  demographics: {
    name, dob, sex,
    address?, phone?, email?,                  # extracted for delta-matching against chart
    emergency_contact?,
    citations: { name, dob, address, phone, email, ... }  # per-field bbox
  }
  chief_concern: string                        # free text
  current_medications: list[{ name, dose?, frequency?, citation }]
  allergies: list[{ substance, reaction?, severity?, citation }]
  past_medical_history: list[{ condition, year?, citation }]
  family_history: list[{ relation, condition, age_at_dx?, citation }]
  social_history: { smoking?, alcohol?, occupation?, citations }
  signature_present: boolean
  signature_citation: { page, bbox } | null
```

Both schemas carry per-field `citation` with `{page, bbox, quote}` so the citation contract (§5) is satisfied at extraction time. Strict mode is **`extra='ignore'`** (Pydantic) / **`.passthrough()`** (Zod). Unknown fields are silently dropped during decode; missing-required-field is still a hard error.

### W2-3. Cost & latency

- **Vision call cost.** Anthropic pricing for Sonnet 4.x with images is roughly an order of magnitude more expensive per page than text-only. A 5-page lab PDF could be ~$0.05–0.15 per extraction.
- **Latency.** PDF Pitfall #2: extraction is the slow part of the flow. P50 budget for `attach_and_extract`: **5–15s** on a typical 1–3 page document; hard ceiling 30s before a "still working…" message replaces the loading state. RAG retrieval is fast (<500ms) once the index is warm.

**Q3 — RESOLVED.**

- **Per-document hard cap: $1.00.** Circuit-breaker. The projected cost of a single extraction (computed from page count + estimated input/output tokens before the API call fires) must be under $1.00 or the extractor refuses with a "document too large for automatic extraction" structured error. Generous enough that no real clinical document hits it; restrictive enough to bound any one accidental upload.
- **No per-patient daily cap.** Not enforced. Per-patient cost still surfaces in observability rollups (`agent_request_log` is already indexed on `(patient_pid, disclosed_at)`) for forensic / cost analysis, but no automated throttle.
- **No site-wide demo budget cap.** Not enforced at the agent layer. Anthropic's account-level spend caps remain available as the operator backstop.

**Cost analysis breakdown** (in `docs/COST_ANALYSIS.md`, per W2 deliverable). All three stages are broken out per the existing 100 / 1K / 10K / 100K user tiers, so the cost projection is a real production artifact rather than a vision-call invoice:

| Stage | Service | Driver | Pricing dimension |
|---|---|---|---|
| Embedding (RAG indexing) | OpenAI `text-embedding-3-small` (Q8) | Corpus size at index time + per-query embed at retrieval time | $/1M tokens |
| Rerank (RAG retrieval) | Cohere `rerank-3` (or fallback) | Per `evidence-retriever` invocation | $/1k searches |
| Synthesizer (W1 carry-forward) | Claude Sonnet 4.x | Per briefing/follow-up turn | $/1M input + $/1M output tokens |
| Vision (W2 new) | Claude Sonnet 4.x with image inputs | Per `attach_and_extract` call | $/1M input (incl. image tokens) + $/1M output |

The W1 §6.1 in-memory counters already roll up tokens + dollars per stage; the new stages plug into the same `Counters` registry. The cost-analysis doc is generated from real run data (LangSmith experiment + per-MR Vitest counters), not invented.

### W2-4. PHI handling for documents

The PDF body itself is PHI. Three new questions:

- **Where do raw uploaded documents live?** OpenEMR's `documents` table is the canonical pointer; the bytes themselves land in **DO Spaces** (S3-compatible) under a per-patient prefix. The agent service does **not** store raw documents — it consumes a signed URL and discards.
- **Q4 — RESOLVED. Vision payload delivery: signed URL (DO Spaces).**
  - Documents are written to DO Spaces at upload time (manual via panel in MVP; later via background sweep).
  - When the extractor needs to call the vision API, it asks OpenEMR for a **time-boxed signed URL** (TTL ≤5 minutes — same order as the JWT — and **single-call**: the signed URL is bound to one request, expires immediately on use).
  - Rasterized page images (PNG/JPEG output from the rasterizer — see below) are uploaded to a **transient bucket prefix** (`spaces://.../transient/<extraction_uuid>/page-N.png`) with the same short TTL signed URL, then the URLs are passed to the Anthropic vision API.
  - Transient prefix has a lifecycle policy: objects deleted after 24h regardless of extraction state. The extractor proactively deletes after success or terminal failure.
  - Trade-off accepted: the document and rasterized images are URL-reachable to Anthropic for the call's duration. Mitigated by short TTL, single-call signing, transient bucket isolation, and a Spaces bucket policy that limits egress to Anthropic's published API egress range (if available) — otherwise unrestricted, which is the realistic operational shape.
  - Cost trade-off: signed URLs avoid the ~4/3× base64 inflation in request payload and let Anthropic stream large images without us materializing them in process memory. At Q2-frozen doc sizes (1–10 pages), this is marginal; at the (B) background-sweep scale (every uploaded clinic document) it matters more.
- **Q4b — Rasterization library: deferred** to "pick the most-maintained when we get there." `pdf2pic` (uses GraphicsMagick), `pdfjs-dist` + `node-canvas`, and `pdf-img-convert` are the realistic options. Decision lands at implementation time; the wrapper interface is `(pdfBytes) => Promise<{page, png}[]>` either way, so the choice is interchangeable.
- **Q5 — RESOLVED. LangSmith vision-call posture: inherit W1 default, suppress all inputs and outputs.** No new behavior — `LANGSMITH_HIDE_INPUTS` / `LANGSMITH_HIDE_OUTPUTS` already on by default; vision-call image inputs and extracted-schema outputs both fall into those slots and are suppressed automatically. LangSmith sees only: tool name, latency, token counts, dollar cost, structured run metadata (page count, doc_type, extractor version, extraction confidence, schema-validation pass/fail). Zero PHI on the wire to LangSmith.
  - Local debug: a `AGENT_DEBUG_VISION_INPUTS=1` flag lets the agent log full vision payloads to its own Pino logger (which is itself PHI-redacted by the existing path-pattern logic) — never to LangSmith. Useful for "the model misread page 3" debugging without weakening the trace posture.
  - W1 §6.1 trace-scan test extended to include vision-call traces in the fixture set so a future contributor who flips the default can't pass CI.

## Phase 2 — Architecture decisions

### W2-5. Multi-agent shape — supervisor loop + invokable ingestion pipeline

**Q6 — RESOLVED.** Two distinct LangGraph apps that share data only through persisted artifacts, not runtime state. **The supervisor is LLM-driven, not rule-based** — non-determinism is a deliberate design choice and the lesson the W2 assignment is testing. Determinism is preserved only where it is load-bearing for safety (verifier, hard stops) or fixed transformations (the ingestion pipeline).

#### (1) Conversational graph — LLM-driven supervisor loop, model-driven retrievers, terminal synthesis

`loadState` and `planContext` are **hoisted out of the graph** into the runner layer. Conversation persistence is runner-side work that wraps the graph invocation; envelope validation is input-parsing. Both stay where they belong; the graph keeps the work it actually does. The runner additionally projects the existing `conversation_messages` table into a `priorTurnContext: PriorTurnContext` slot on `BriefingState` before invoking the graph — user turns replay verbatim, assistant turns replay as `{citations, facts}` only (no prose). The supervisor and synthesizer both read it; the asymmetric replay shape preserves dialog-thread signal that isn't recoverable from data while keeping derived prose out of the model's structured-output channel. See `W2_ARCHITECTURE.md` §"Prior-turn context".

`retrieve` is **renamed `retrieveChart`** and its first invocation runs deterministically with the standard fan-out (W1 carry-forward) so the supervisor has *some* chart context to reason over on its first iteration. Every retriever call after that — including any subsequent `retrieveChart` re-fetches with narrower categories — is model-driven (the model decides which tools to call and whether more information is needed).

```
START
  ↓
retrieveChart (deterministic — first call only, W1 fan-out)
  ↓
supervisor (LLM loop, max 10 iterations) ─┬→ kickoffExtraction        (when an unprocessed doc is referenced)
                                           │   ↓ awaits ingestion pipeline
                                           │   ↓ back to supervisor
                                           │
                                           ├→ retrieveChart            (model-driven re-fetch with narrowed categories)
                                           │   ↓ back to supervisor
                                           │
                                           ├→ documentEvidenceRetriever (model-driven query over extraction_artifacts)
                                           │   ↓ back to supervisor
                                           │
                                           ├→ evidenceRetriever         (model-driven query over the guideline corpus)
                                           │   ↓ back to supervisor
                                           │
                                           ├→ <UC3/4.6.5/4.6.6 deterministic branches>
                                           │   ↓ back to supervisor
                                           │
                                           └→ synthesize  ← terminal handoff; supervisor exits the loop
                                               ↓
                                           verify
                                               ↓
                                           format
                                               ↓
                                           persist
                                               ↓
                                             END
```

**The supervisor is an LLM call with structured-output handoff selection.** Each iteration:

1. Inputs to the supervisor LLM: current chart snapshot, user envelope, accumulated retriever outputs, supervisor's own decision history this turn, a closed enumeration of available handoffs with brief descriptions.
2. Output is Zod-coerced to a structured shape: `{handoff: <closed enum>, reason: string, args?: object}`. The model picks from a finite set; it cannot invent handoffs.
3. The chosen handoff runs; control returns; supervisor LLM runs again with updated state.
4. Loop terminates when the supervisor picks `synthesize` (terminal handoff) or hits the iteration cap.

**Iteration cap: 10.** Configurable, eval-pinned. If the cap is hit without the supervisor picking `synthesize`, the graph forces a transition to synthesize with whatever was retrieved (with a `cap-hit` flag on the trace metadata so the case is investigable). Eval cases pin both the happy path (supervisor reaches synthesize on its own within the cap) and the cap-hit path (synthesize fires deterministically when the cap binds).

**Model-driven retrievers.** The retriever nodes themselves accept structured arguments from the supervisor's `args` field. For example:
- `documentEvidenceRetriever(args)` where `args = { query: string, doc_types?: string[], lookback_days?: number, top_k?: number }`. The model picks the query, the categories, the recency window.
- `evidenceRetriever(args)` where `args = { query: string, top_k?: number, source_filter?: string[] }`. The model picks the query and (optionally) restricts to specific corpus sources.
- `retrieveChart(args)` after the first invocation: `args = { categories: ('diagnosis' | 'medication' | 'allergy' | 'lab' | 'encounter' | 'reminder' | 'medication_statement' | 'appointment')[] }`. The first call ignores `args` and runs the standard fan-out; subsequent calls honor the model's narrowed category list.

The first `retrieveChart` is the only deterministic data-retrieval action in the graph. Everything downstream is the model deciding what context it needs.

**Closed handoff enumeration.** The supervisor cannot pick arbitrary actions — it picks from `{kickoffExtraction, retrieveChart, documentEvidenceRetriever, evidenceRetriever, prescriptionChangeBranch, reminderBranch, medicationStatementBranch, synthesize}` enforced by Zod. Adding a handoff means updating the enum + the manifest description + the eval cases.

**Decision rationale is required.** The supervisor's `reason` field is non-empty by Zod contract; it explains why this handoff was picked given current state. This becomes part of the trace and is what the demo shows for "supervisor decided X because Y."

**Inspectability via LangSmith.** Every supervisor invocation logs as a structured trace event with input state observed (PHI-suppressed per W1 default), the handoff manifest presented to the model, the chosen handoff, the model's free-text reason, the args passed downstream, the iteration counter, and the LLM's token usage and dollar cost. Every retriever call is similarly traced with its model-driven args. The supervisor's full decision chain per turn is reconstructable from LangSmith without replaying the call.

This is the load-bearing answer to the PDF's "supervisor must not be a black box" requirement — not by removing the LLM, but by structurally constraining its output to a closed enumeration, requiring an explicit rationale per decision, and instrumenting the entire decision chain in LangSmith so every choice is post-hoc inspectable.

**Terminal-handoff exit.** `synthesize` is the only handoff that doesn't return to supervisor — it transitions directly to `verify`. Loop termination is structurally enforced through the closed enumeration (the model picks `synthesize` to exit) plus the iteration cap (graph forces synthesis at iteration 10 if the model hasn't picked it). Cycle detection — the model picking the same handoff twice with no meaningful state change — is logged as a `degenerate-loop` warning but does not terminate; the iteration cap absorbs it.

#### What stays deterministic

- **Ingestion pipeline.** Sequential transformations with no agent-judgment decision points. See §(2) below.
- **Verifier.** Source-reference resolution per `source_type` is structural, not probabilistic. PRESEARCH §10's "verified or not — no probabilistic confidence" rule is unchanged.
- **Hard clinical stops.** Missing-allergies / missing-medications fail-closed are safety floors, not routing decisions. They run deterministically inside the verifier.
- **First `retrieveChart` invocation.** Standard fan-out so the supervisor has chart context on iteration 1. Subsequent re-fetches are model-driven.
- **Cap-hit forced synthesize.** If the supervisor doesn't terminate by iteration 10, the graph forces it.

The rule of thumb: **non-deterministic where the agent is making judgments about what to do next; deterministic where we're enforcing safety or running fixed transformations.**

#### (2) Ingestion pipeline — separate compiled LangGraph app, shared by all invokers

```
ENTRY (one of three invokers — see below)
  ↓
rasterize        ← PDF bytes → page PNGs (signed-URL upload to Spaces transient prefix)
  ↓
vision           ← per-page extraction with strict schema + bboxes (Anthropic VLM)
  ↓
schemaValidate   ← Zod parse w/ extra='ignore' (Q2c); on fail, structured error artifact
  ↓
patientMatch     ← compare extracted demographics to chart; on mismatch, refuse + emit error
  ↓
persist          ← FHIR resources + extraction_artifact row, both with source_document_uuid
  ↓
emitDeltas       ← compare extracted facts to chart, mark deltas for UI surfacing
  ↓
EXIT (returns artifact_id; emits DocumentExtractedEvent)
```

**Three invokers, one pipeline:**
1. **Conversational supervisor's `kickoffExtraction` handoff** (path A — manual upload during a conversation). Supervisor calls `await pipelineGraph.invoke(...)` synchronously, pumps progress events back over SSE so the panel renders "Extracting document…" → "Document evidence available, drafting briefing…".
2. **OpenEMR `DocumentUploadedEvent` listener** (path B — front-desk autosweep, deferred to a later phase). Same pipeline call, system-actor JWT, no conversation in scope.
3. **CLI replay** for debug, regression reproduction, and eval re-runs.

**Idempotency** is enforced at pipeline entry: the lookup key is `(document_hash, extractor_version)`. If an artifact already exists for that key, the pipeline returns the cached artifact_id without re-running. Concurrent invocations across paths A and B race-safely via an advisory lock keyed on `document_uuid` in agent Postgres.

**Failure isolation.** Pipeline failure (vision API down, schema invalid, patient mismatch) emits a structured-error artifact with reason and never poisons chart state. The conversational graph's supervisor sees the failed-artifact state and routes around it — the chart-only briefing renders with a Gap chip ("Document attached, extraction unavailable").

#### (3) The "two workers" defense for the PDF

The PDF requires "supervisor + 2 workers" with logged handoffs. We have exactly that, in the right place:
- **Workers** = `evidenceRetriever` (guidelines RAG) and `documentEvidenceRetriever` (extracted-facts retrieval). Both are runtime graph nodes, both share the `(query, scope) → CitedSnippet[]` interface, both produce `SourceReference[]` consumed by the verifier.
- **Supervisor** = the LLM-driven routing node. Closed-enum handoff selection (cannot invent actions), Zod-enforced rationale per decision, iteration cap of 10 with cap-hit forced synthesize, every iteration logged to LangSmith with state observed, chosen handoff, rationale, args, and token usage. Eval cases pin plausibility (chosen handoff in case's allowed set), not exact-match.
- **The intake-extractor is producer-side infrastructure**, not a worker in the answering graph. It's named, observable, has its own logged emit events (`DocumentExtractedEvent`), and is invokable from any of three triggers — but it doesn't share runtime state with the conversational graph. Producer-consumer separation is what lets path (B) slot in later without rebuilding the agent.

#### (4) State persistence boundaries

| Graph | State lives in | Checkpointer |
|---|---|---|
| Conversational | LangGraph Postgres checkpointer keyed on `thread_id = conversation.id` (W1 carry-forward) | W1 setup unchanged |
| Ingestion pipeline | `extraction_artifacts` table (agent Postgres) + FHIR resources + DocumentReference (OpenEMR) | None at LangGraph layer — pipeline is short-lived and idempotent on `(document_hash, extractor_version)` |

The two graphs never share LangGraph state. They share data exclusively through persisted artifacts, which is the same producer-consumer pattern Phase 5's `agent:precompute-day` already uses for schedule briefings.

### W2-5b. Unified `SourceReference` shape (folds in Q10)

One citation shape, three `source_type` values, used by every retriever and indexed uniformly by the verifier. This is the load-bearing data contract for the Week 2 citation requirement.

```ts
interface SourceReference {
  source_type: 'chart' | 'extracted_document' | 'guideline';

  // Stable id of the source.
  //   chart              → FHIR resource uuid (Patient/Observation/Condition/...)
  //   extracted_document → extraction_artifact uuid
  //   guideline          → corpus chunk id
  source_id: string;

  // Where inside the source the cited content lives.
  // Optional fields apply only to certain source_types — enforced by Zod refinement.
  locator: {
    page?: number;          // extracted_document only — required when source_type='extracted_document'
    bbox?: [x, y, w, h];    // extracted_document only — required when source_type='extracted_document'
    section?: string;       // guideline only — required when source_type='guideline'
    field?: string;         // semantic field name; chart uses 'medication.name', extracted uses 'results[3].value'
  };

  // Exact text or value cited. For chart, the field's stored value. For
  // extracted_document, the OCR'd quote at the bbox. For guideline, the chunk
  // substring the synthesizer is grounding on.
  quote: string;

  // Vision-extracted only. Chart and guideline sources omit this — chart is
  // deterministic, guideline confidence is retrieval-side metadata in `meta`.
  confidence?: number;

  // Source-type-specific metadata for debugging/observability. Never inspected
  // by the verifier or renderer.
  meta?: {
    document_uuid?: string;       // extracted_document → links to DocumentReference
    extractor_version?: string;
    rerank_score?: number;        // guideline only
    record_recorded_at?: string;  // chart only
  };
}
```

**Per-source-type verification rules:**

| `source_type` | Verifier resolution |
|---|---|
| `chart` | `source_id` must be in indexed `BriefingSnapshot` (W1 carry-forward); per-category content check (medication name, lab analyte+value, etc.) |
| `extracted_document` | `source_id` must be in this turn's `extraction_artifacts`; `locator.page` and `locator.bbox` must equal the recorded extraction's bbox/page (no fabricated bboxes); `quote` substring-matches the extracted value at that field |
| `guideline` | `source_id` must be in this turn's retriever output; `quote` substring-matches the chunk text |

**Renderer dispatch.** One chip component, three click handlers driven by `source_type`:
- `chart` → links to OpenEMR record page (W1 behavior carries forward).
- `extracted_document` → opens PDF.js overlay at `(page, bbox)`, highlights the cited region.
- `guideline` → opens a section-snippet popover with the corpus document title.

**Backward compatibility.** W1's `SourceReference` today is `{system, recordType, recordId, field, recordedAt}`. The W2 shape supersedes it cleanly by rename:
- `recordType` → `source_type` (with value `'chart'` for all W1 references)
- `recordId` → `source_id`
- `field` → `locator.field`
- `recordedAt` → `meta.record_recorded_at`
- `system` (ostensibly the FHIR system URI, in practice always implicit) is dropped — the source_type discrimination already encodes the system.

This lands as a single coordinated migration: PHP `SourceReference` value object renames its fields; TS Zod schema renames likewise; verifier index keys re-key; LangSmith dataset version bumps to `clinical-copilot-uc1-golden-v4`. The contract test (`AgentTokenContractFixtureTest` ↔ `agent/tests/snapshot/contract.test.ts`) catches any drift between the two sides on the same commit.

**Locator polymorphism enforcement.** A Zod refinement on `SourceReference` validates that the `locator` shape is consistent with `source_type`:
- `source_type === 'extracted_document'` → both `locator.page` and `locator.bbox` are required.
- `source_type === 'guideline'` → `locator.section` is required.
- `source_type === 'chart'` → `locator.field` is required.

Bad combinations are rejected at parse time, not at render or verify time. This keeps the unified shape from becoming a soup of optional fields that nobody validates.

### W2-6. Vision LLM selection

**Q7 — RESOLVED. Claude Sonnet 4.x for vision extraction.**

- Same Anthropic SDK (`@langchain/anthropic`) and same model family as the W1 synthesizer — no new vendor for compliance review, no second retry/structured-output convention to maintain.
- BAA framework already in place (W1 §12).

- Estimated cost ~$0.03–0.15 per document on Q2-frozen sizes (1–10 pages), comfortably inside the Q3 $1/doc hard cap.

- **Open-source VLM (Qwen2-VL, Pixtral, self-hosted or via a third-party host).** Cheaper per call but adds a deployment surface, a separate auth story, no current BAA, and more eval flakiness. Defer until cost actually constrains the architecture.
- **OpenAI GPT-4o / 4.1 with vision.** Comparable capability and pricing; OpenAI has BAAs. Real downside is two SDKs and two structured-output conventions to maintain. Worth revisiting only if Sonnet shows specific failure modes in evals (e.g., handwritten intake forms).

### W2-7. Hybrid RAG design

Required: keyword + dense retrieval, rerank, top-k snippets fed to the answer model. Stretch: ColQwen2 / multi-vector (we say no — see Pitfall §6).

**Stack questions:**

- **Q8 — RESOLVED. Embedding model: OpenAI `text-embedding-3-large` (3072d).** ~$0.13 per 1M tokens. Higher quality than `-small` on technical/medical text; embedding cost is rounding-error against the W2 cost model at the Q9-locked corpus size (100–300 chunks). New vendor: OpenAI, configured solely for embeddings — no other OpenAI usage in scope. `OPENAI_API_KEY` env var added to the agent service.
- **Vector store — RESOLVED. Pinecone (managed).** Reasoning:
  - **No PHI in the index.** The guideline corpus is public reference material (USPSTF, ADA, etc.). Per-patient extraction artifacts stay in agent Postgres — they don't enter Pinecone. So the trust-boundary argument that drove agent Postgres ("compromised agent reaches only conversation data, not patient records") doesn't change shape because of Pinecone — Pinecone holds only the reference corpus.
  - **Operationally simpler than `pgvector` at 3072 dims.** Avoids the `pgvector` index-type considerations at 3072d (ivfflat cap, hnsw build constraints, halfvec choice). Pinecone supports 3072d natively with no index-tuning at our corpus size.
  - **Performance.** Pinecone's serverless tier is purpose-built for vector search; latency at our corpus size is essentially constant and well under our retrieval budget (<500ms).
  - **Operator learning lever.** Working with a managed vector DB is an explicit goal alongside shipping the feature.
  - **Cost.** Pinecone serverless bills on stored vectors + reads. At 100–300 chunks and our PR-cadence read volume, the bill is dollars/month, not thousands.
  - **New env vars:** `PINECONE_API_KEY`, `PINECONE_INDEX_NAME`. `PINECONE_NAMESPACE` defaults to `guidelines-v1` and bumps with corpus version per Q19.
- **Hybrid retrieval shape with Pinecone.** Pinecone owns the dense leg natively. The sparse leg lives separately:
  - **Option A (recommended): Pinecone hybrid index.** Pinecone supports sparse-dense hybrid indices via the `pinecone-text` SDK — sparse vectors generated from BM25 over the corpus text live alongside dense vectors in the same index. One query returns fused results. Single vendor for retrieval; rerank still flows through Cohere on top of Pinecone's top-20.
  - **Option B (fallback): keep sparse on agent Postgres `tsvector`** + dense on Pinecone, fuse with reciprocal rank fusion in app code. More flexible (Postgres FTS is more expressive than BM25 over arbitrary text), more code to maintain.
  - **Recommendation: A.** The corpus is small enough that Postgres FTS's expressivity gain is theoretical, and "single vendor for retrieval" is the simpler operational story.
- **Reranker.** Cohere `rerank-3` (PDF mentions Cohere by name; well-established API; ~$1 per 1k searches). Voyage AI `rerank-2` is a newer alternative but adds another vendor. **Recommendation:** Cohere `rerank-3` to track the PDF's example.
- **Hybrid fusion.** Reciprocal rank fusion (RRF) with k=60 on the union of top-20 from sparse + top-20 from dense, then rerank top-10 down to top-3. Standard recipe; no novelty needed.

**Q9 — RESOLVED. Corpus is curated, not bulk-ingested. Sources are added one at a time, with eval validation between each, in the priority order below. The MVP ships with USPSTF only; subsequent sources are separate sub-phases in the implementation plan.**

### W2-9. Persistence path for extracted facts

**Q11 — RESOLVED. Tiered persistence with explicit confirmation gate ((C) from the analysis).**

Every extracted fact must:
1. Be linked back to the source DocumentReference (traceability).
2. Not duplicate existing chart records.
3. Be queryable by the existing snapshot/adapter layer so the verifier indexing keeps working.
4. **Not auto-write to the canonical clinical record without a clinician affirming it** (this is the W2 addition — clinical-safety gate).

#### Three persistence tiers

**Tier 1 — Source document (always lands in OpenEMR, no clinical risk).**
- `DocumentReference` for the source PDF / image.
- Bytes in DO Spaces (Q4) under per-patient prefix.
- Categorized via OpenEMR's existing `categories` / `categories_to_documents` so it shows up in the existing document UI.
- Fires the existing `documents.post_insert` event, which (in a later phase) is what path-B autosweep will listen to.

**Tier 2 — Extraction artifacts (land in agent Postgres, never write to chart).**
- New table `extraction_artifacts(artifact_id PK, document_uuid FK to OpenEMR DocumentReference, doc_type, extractor_version, schema_json JSONB, deltas_json JSONB, status, created_at, confirmed_at NULL, confirmed_by_user NULL)`.
- `schema_json` carries the strict-schema extraction with per-field bbox + page + quote — the source of truth for the `documentEvidenceRetriever` and the `SourceReference.locator` data the verifier resolves against.
- `deltas_json` is the diff between extracted facts and chart state, computed by `emitDeltas` at the end of the pipeline.
- `status` is one of `pending_confirmation` | `confirmed` | `rejected` | `superseded`. Pipeline writes always start at `pending_confirmation`.
- Idempotency key UNIQUE on `(document_hash, extractor_version)` — re-running the pipeline against the same document is a no-op.
- This is the data the synthesizer cites with `source_type='extracted_document'` — citing extracted facts is allowed at any tier; promoting them to chart records is the gated step.

**Tier 3 — Chart records (land in OpenEMR only on explicit confirmation).**
- A clinician (Dr. Patel, in the panel) reviews the extracted-facts delta and clicks "accept extracted facts" — either per-fact or per-extraction.
- On confirmation, derived FHIR resources are written:
  - **Lab PDF** → one `DiagnosticReport` per lab panel + one `Observation` per result via the new `ObservationLabWriteService` (Q12 RESOLVED below).
  - **Intake form** → derived facts split:
    - allergies → `lists` row (allergy type) with new `source_document_uuid` column.
    - patient-reported medications → `lists` row as `MedicationStatement` (matches W1 §4.6.4 — patient-reported, not Rx).
    - past medical history → `lists` row (medical_problem) with `source_document_uuid`.
    - family history → `family_history` table with same lineage column.
- Each chart record carries `source_document_uuid` linking back to the Tier-1 DocumentReference.
- Each chart record fires the existing OpenEMR write events (so other downstream consumers — quality measures, alerts, exports — see them as normal chart updates).
- `extraction_artifacts.status` flips to `confirmed`, `confirmed_at` and `confirmed_by_user` populated.

**Demographics deltas (Q2b)** are surfaced but never auto-promoted. The intake-form extraction artifact carries them; the synthesizer flags them in the briefing as a "needs-confirmation delta" with the suggested update; promoting an address change to the chart is an explicit clinician action, same gate as clinical facts. Auto-updating chart demographics from an extracted form is out of W2 scope.

#### Why (C) tiered persistence with a confirmation gate

- **Clinical safety.** Wrong-extraction-into-the-chart is a real harm scenario (model misreads "no penicillin allergy" as "penicillin allergy" and the chart now shows a phantom allergy). The confirmation gate keeps the canonical record clean.
- **Reversibility by design.** Anything in agent Postgres can be deleted without touching OpenEMR. Anything that's been promoted to chart goes through OpenEMR's normal undo paths (which exist for all FHIR resources).
- **Round-trip story for the PDF spec.** "Uploaded documents and derived observations must round-trip through OpenEMR" — DocumentReference always lands in OpenEMR; derived FHIR resources land in OpenEMR through the confirmation path. The path is supported and demoable; the safety gate is the production stance.
- **The demo still demos.** MVP demo runs the auto-write path against synthetic patients with the confirmation step shown explicitly — "Dr. Patel reviews the extraction and accepts." That's a stronger demo than silent auto-writes because it shows the safety surface working as intended.
- **Production-readiness note.** The `W2_ARCHITECTURE.md` documents the confirmation gate as the production stance. A future operator could relax it (auto-confirm on high-confidence extractions) per their clinical-safety review, but the default is gated.

#### Schema migration

Doctrine migration under `db/Migrations/Version<...>.php`:
- New column `source_document_uuid VARCHAR(36) NULL` on `lists`, `family_history`, `procedure_report` — the FHIR uuid of the source DocumentReference.
- New table `extraction_artifacts` in agent Postgres (TS-side migration via the LangGraph-checkpointer pattern: idempotent `CREATE TABLE / CREATE INDEX IF NOT EXISTS` at agent boot).
- Index on `(patient_pid, doc_type, status)` for the documentEvidenceRetriever's per-patient lookup.

#### Q12 — RESOLVED. New `ObservationLabWriteService`.

A new service under `interface/modules/custom_modules/oe-module-clinical-copilot/src/Service/` (or in OpenEMR core if scope permits — TBD at implementation time). ~150 lines:
- Insert into `procedure_report` (one row per lab panel) and `procedure_result` (one row per analyte value).
- Validate the input shape via a typed DTO before writing — refuses partial / malformed data.
- Idempotent on `(source_document_uuid, panel_code, collection_date)` — re-confirming an already-promoted extraction is a no-op.
- Fires `procedure_report.post_insert` event so other listeners see the write as normal.
- PSR-3 logging; injected `ClockInterface` for deterministic tests; the W1 `BaseService` pattern.

Inline SQL via `QueryUtils` was rejected because the procedure tables have non-trivial relationships (`procedure_order_code` for LOINC lookup, `procedure_report.procedure_order_id` for the pending-order link path) and a typed service is the right encapsulation boundary.

PHPUnit isolated test that:

### W2-10. Verification design extensions

The W1 verifier already enforces "every claim resolves to a source." W2 extends:

- **Vision-extracted claims.** Every fact in a `lab_pdf` or `intake_form` extraction must have a non-null `citation.page` and `citation.bbox`. The verifier rejects claims whose document citation can't be resolved against the indexed extraction set. Today's `verifyLedger` indexes the snapshot — it needs to additionally index the active extraction's facts so a claim like "the patient reports a penicillin allergy [intake_form:doc-123]" resolves.
- **Guideline claims.** A new claim category `guideline` whose verifier check is: the cited chunk id exists in the `evidence_retriever` output; the quote substring appears in the chunk text. Reject otherwise.
- **Evidence-vs-record separation.** PDF: "Every answer must separate patient-record facts from guideline evidence." The `Format` node groups claims by `source_type`: chart-record claims under "What's in the chart"; document-extracted claims under "What's in the new documents"; guideline claims under "Evidence." The UI renders three sections.

**Q14 — RESOLVED. Low-confidence extraction is rejected at fact level, with an allergy-specific exception that escalates to category-level fail-closed.**

#### Confidence signal — combined per-field self-report + derived signals

A claim is "low-confidence" if **any** of:
- **Self-reported per-field confidence** from the VLM is below the threshold. Soft signal — known to be poorly calibrated, but useful in aggregate.
- **Schema-validation produced a warning** (e.g., a required field came back null and was filled by a fallback, an enum value didn't match exactly).
- **Patient-match was partial** (e.g., name matched but DOB differed by a day — typo vs. wrong-patient ambiguity).

The first is a continuous score; the second and third are derived booleans. The verifier ORs them together — any one failing marks the field low-confidence.

#### Threshold — 0.7 self-reported as starting point, tuned against evals

The 0.7 threshold is a starting point, not a final number. Tuned as a hyperparameter:
- Pinned to a specific commit in `agent/src/verify/confidenceThresholds.ts`.
- Evals (the 50-case suite) re-run on threshold changes; rubric scores tell us whether tightening or loosening helped.
- Per-doc-type thresholds allowed if evals show different optimal points (intake-form allergies might need a tighter threshold than lab-PDF analyte values).
- The threshold itself is logged on every trace as a metadata field, so threshold-shifts are observable in the cost/quality analysis.

#### Fail-closed scope — fact-level, with allergy exception

**Default behavior: fact-level rejection.** A low-confidence extracted fact is dropped from the response. The verifier rejects any claim depending on that fact with reason `low-confidence-extraction`. The user sees a Gap chip on the affected fact, not the whole section. Other facts in the same extraction render normally if they passed the confidence check.

**Allergy exception: category-level fail-closed.** If a low-confidence *allergy* fact appears in an intake form extraction, the entire medication section in the briefing fails closed — same behavior as W1's "missing allergies" hard stop, applied symmetrically across chart-side and document-side gaps. The reasoning is the W1 safety floor: missing-an-allergy is unsafe regardless of where the gap is, and a low-confidence allergy extraction is functionally equivalent to a missing allergy from the medication-safety perspective. The user sees the standard "medication summary withheld — allergy data unverified" Gap chip on the medication section.

#### Observability

- **Confidence per field** logged on the trace as run metadata (LangSmith).
- **Schema-validation warnings** logged.
- **Patient-match score** logged.
- **`low-confidence-extraction` rejection rate** logged as a counter in the existing W1 §6.1 observability path. A rising rejection rate is the leading indicator that the threshold needs tuning or the model has drifted.

### W2-11. Observability extensions

W1 already logs per-tool latency, tokens, cost, claim counts, verification pass/fail, prompt-injection failures. W2 adds:

- **Extraction confidence per field.** The vision LLM returns a per-field confidence (or we ask it to). Logged on the trace; surfaces in the eval rubric `factually_consistent` (PDF requirement).
- **Retrieval hits.** For each `evidence-retriever` call: top-k chunk ids, rerank scores, final selected ids. Logged.
- **Supervisor handoffs.** Each routing decision logged as a structured trace event (see §5).
- **Vision-call PHI suppression.** See Open Q5 above — likely full input suppression, not redacted thumbnails.

`no_phi_in_logs` is a cross-cutting assertion run on every case (extends the W1 §6.1 phiTraceScanner to vision-call traces). 50 cases × 5 rubrics = 250 boolean assertions, ~80 of which are "this rubric is the case's reason for existing"; the rest are background safety nets that catch leak-from-anywhere bugs.

#### Real model in CI — for all 50 cases

**Per-MR CI runs every case against the real model**, including the real vision LLM (Q7 Sonnet 4.x), real embeddings (Q8 OpenAI `text-embedding-3-large`), and real Cohere rerank. This deliberately diverges from the W1 stubbed-synthesizer pattern documented in CLAUDE.md — we're trading determinism and per-PR cost for a hard gate that catches model-side regressions, not just code-side ones.

**Consequences accepted:**
- **Cost per PR.** ~50 cases × ~$0.05 average per case (vision dominates) = ~$2.50 per PR run. Bounded by the per-document cap from Q3. A per-PR hard cap (~$5) lives at the CI layer to prevent a runaway loop from running up a bill.
- **Latency per PR.** Sequential ~8 minutes; parallelized to 3–5 minutes. Slower than W1's ~3-second stubbed gate, but inside the acceptable window for a merge gate.
- **Determinism.** Real-model variance can flip rubric outcomes case-by-case. Mitigated by:
  - Boolean rubrics designed to be **structural where possible** (`schema_valid` parses or doesn't; `citation_present` either includes a SourceReference or doesn't). These survive model variance cleanly.
  - Phrasing-sensitive rubrics (`safe_refusal`, `factually_consistent`) use **substring/structural matchers** rather than exact-string equality — e.g., refusal cases assert that the response contains a refusal-shaped phrase from a closed set, not an exact wording.
  - Temperature=0 on every model call. Anthropic's seed support is best-effort; we don't rely on it for determinism, but we set it where supported.
  - The 5%-regression-threshold on the rubric category (PDF requirement) absorbs the residual variance — single-case flakes don't fail CI, but a category-wide drop does.
- **Stubbed versions exist alongside real-model cases.** Stubbed versions live under `agent/evals/cases/<suite>/stubbed/` for fast local iteration during development. They're not the CI gate — the real-model versions under `agent/evals/cases/<suite>/` are. Stubbed versions are the developer's inner loop; the real-model gate is the merge gate.

**The PDF's hard gate** ("we'll inject a small regression and confirm CI fails") is satisfied either way — most plausible regressions are in the deterministic gate logic (loosened verifier, missing citation requirement, etc.) which the structural rubrics catch regardless of model variance.

#### Ground-truth source — bake into the seeding pipeline

The seed pipeline (W1 `bin/seed/PatientArchetype.php`, `db/seeds/`) currently produces synthetic charts. **W2 extends it to also produce synthetic documents** keyed to each archetype. Each archetype gets a deterministic set of associated documents (a diabetic patient's archetype includes a recent lab PDF showing elevated A1c; the complex-elderly archetype includes an intake form documenting medication adherence concerns; etc.).

**Document fixture sources, layered:**

1. **Real public-domain examples** as templates. USPSTF, CDC, and other federal sources publish sample lab reports and intake forms; these become the visual templates. Real templates capture the messy realities of actual clinical documents (multi-column layouts, footers, low-contrast scans) that synthesized examples miss.
2. **Synthesized fillings against those templates.** A new generator (probably under `bin/seed/DocumentGenerator.php` or a sibling under `agent/evals/fixtures/document_extraction/`) populates the templates with archetype-derived data: a `Diabetic` archetype's lab PDF carries the same archetype's `requiredAnalytes()`; the values come from the same PRNG seed that drives chart generation.
3. **Hand-authored regression fixtures.** Every prod incident captured as a hand-authored fixture under `agent/evals/fixtures/document_extraction/regression-<id>.json` plus a Vitest case (mirrors W1 §"Agent evals" regression-fixture pattern).

**Why bake into the seeding pipeline:** the same seed run produces a chart + its associated documents, which means eval cases can assert end-to-end consistency without coordinating two independent fixture sources. The `(archetype, prng_seed) → (chart, documents)` deterministic mapping is the load-bearing property; the regenerator script enforces it.

The hand-authoring effort is bounded — the W2 build adds the generator and the document templates once, and every archetype + every future fixture inherits both for free.

#### Boolean rubrics — implementation

Each rubric is a pure function `(case, agent_output) → boolean`. Implemented under `agent/evals/cases/document_extraction/` (per-MR layer) and rolled up in `agent/evals/runners/documentExtractionSuite.ts` (LangSmith experiment layer). No LLM-as-judge — the PDF explicitly warns against it without clear rubric.

Per-category baselines committed to `agent/evals/baselines/document_extraction_v1.json`. Rebaseline only via deliberate `evals:rebaseline` runs. CI fails if any rubric drops >5% from baseline or below pass threshold.

#### Regression-injection drill

The PDF's hard-gate test: graders introduce a regression and confirm CI fails. We pre-test ourselves before submission by deliberately weakening the verifier, watching CI go red, then reverting. The drill lives in `docs/RUNBOOK.md` as a documented procedure with the specific weakening to apply.

### W2-15. Security considerations specific to W2

- **Prompt injection in scanned documents.** A document image can carry adversarial text ("ignore prior instructions and …"). The vision LLM is more vulnerable than the synthesizer because the prompt and the data are interleaved. Mitigation: same tag/delimiter pattern as W1 — system prompt names the delimiter, document contents are wrapped, schema-only output. **And** the verifier is the second line: a fabricated extraction can't carry a real `bbox` that maps to a real region of the document, so claims that don't bbox-match get rejected.
- **PHI in vision payloads.** See Open Q5.
- **Document upload AuthZ.** The upload endpoint must check that the acting user can write to the patient's chart, the same way OpenEMR's existing document UI does. Reuse `AclMain::aclCheckCore` — same call site as `AgentSnapshotController`.
- **MIME enforcement.** Only `application/pdf` and `image/{png,jpeg,tiff}` accepted at the upload endpoint. Validated by content sniff, not extension.

### W2-16b. Click-to-source UI (Q17)

**Q17 — RESOLVED.** Three layers in the panel UI, each backed by a different `source_type` from the unified `SourceReference` shape (Q6/§W2-5b).

#### Layer 1 — bbox overlay for `extracted_document` chips

- **Trigger:** click `[source]` on a claim with `source_type='extracted_document'`.
- **Layout:** **side-by-side pane** opens to the right of the chat thread. PDF viewer lives in the pane; chat thread remains visible and scrollable on the left. No modal — the clinician can read the briefing and the PDF at the same time. The panel layout widens to accommodate; both panes resize proportionally.
- **PDF rendering:** PDF.js (Mozilla, MIT, client-side). The full multi-page document loads, **pre-scrolled** to the cited page so the clinician can flip pages naturally without re-fetching. PDF.js's built-in pagination handles flipping.
- **Highlight:** the cited bbox is rendered as a translucent rectangle overlay on the cited page. Clicking elsewhere in the document doesn't dismiss the highlight; clicking another `[source]` chip moves the highlight (and pre-scrolls again if the new citation is on a different page).
- **Auth:** PDF bytes fetched from OpenEMR's existing document-download endpoint (`/api/patient/{pid}/document/{did}`), authorized by the existing OpenEMR session — same trust path as the rest of the panel. No new auth surface.
- **Close behavior:** an X on the pane returns to chat-only width. Clicking another extracted-document chip while the pane is open swaps the document/page/bbox in place; clicking a non-extracted chip closes the pane.

#### Layer 2 — section-snippet popover for `guideline` chips

- **Trigger:** click `[source]` on a claim with `source_type='guideline'`.
- **Layout:** lightweight popover anchored to the chip — no full-pane reveal. Popover contains:
  - The cited chunk text (full text of the chunk, not just the substring quote).
  - The section anchor (e.g., "ADA-2024 §6.5").
  - The publication name and year.
  - Where available, a link out to the published guideline (clicked-out opens in a new tab).
- **No PDF viewer** — guideline chunks are already text; rendering them in PDF.js would be ceremony.
- **Dismiss:** click outside the popover closes it. Clicking another guideline chip swaps the popover content.

#### Layer 3 — inline per-fact accept/reject (Q11 Tier-3 promotion)

- **Placement:** **inline** in the briefing. Each extracted fact in the "Documents say…" section carries a small accept/reject button group next to it.
  - Discoverable for the demo — clinician sees the gate as they read the briefing, no separate tab to find.
  - Matches the natural review-as-you-read flow rather than batch-at-end.
- **Controls per fact:** "Accept" (promotes to chart record per Q11 Tier 3 — fires `ObservationLabWriteService` for labs, list-row inserts for allergies/meds/problems/family history); "Reject" (marks `extraction_artifacts.status = 'rejected'`, fact is dropped from future briefings).
- **No batch operations in MVP.** Per-fact only; "accept all" / "reject all" is post-MVP.
- **Confirmation feedback:** on accept, the fact transitions to a chart-source chip (`source_type='chart'`) on the next briefing turn — the same fact now cites the new FHIR record. Clinician sees the round-trip happen.
- **Demographics deltas (Q2b)** carry their own inline accept/reject — accepting writes the address/phone/email update to the patient demographics row; rejecting marks it dismissed for this visit. This is the Q2b "needs-confirmation delta" surface made concrete.

#### Layer 0 — W1 carry-forward (unchanged)

`source_type='chart'` chips continue to render the W1 behavior: link to OpenEMR record page where a URL exists, tooltip-only otherwise. No change.

#### Implementation notes

- **PDF.js bundle.** Lazy-loaded; not pulled into the main panel JS bundle. First click on an extracted-document chip triggers the dynamic import. Keeps the W1 panel's first-paint latency unchanged.
- **Bbox coordinate space.** PDF.js renders pages at a viewport-scaled size; the extractor returns bbox in the underlying PDF point space. The renderer multiplies by the viewport scale at draw time. Pinned by an early eval case (one fixture, one citation, asserts the highlighted region matches the expected pixel position to within tolerance).
- **Side-by-side responsive behavior.** Below a panel width threshold (e.g., 1200px) the side-by-side falls back to a stacked layout (PDF below chat). The mobile case isn't a W2 priority but the layout shouldn't break.
- **Tests.** Render-test coverage in `tests/Tests/Isolated/Modules/ClinicalCopilot/` pins the data-attribute anchors PDF.js mounts to (same pattern as W1's `PanelTemplateTest`); functional behavior pinned by Vitest cases that exercise the click-handler-to-state transitions with PDF.js stubbed.

## Risks (known unknowns)

- **PDF Pitfall #1 — scope creep.** Two doc types reliably > five doc types unreliably. Hold the line at `lab_pdf` + `intake_form` until eval is green; the third (referral fax / med list) is gated behind that.
- **PDF bbox overlay underestimate.** The bbox-from-VLM contract is not standardized. If the model returns box coordinates in token-relative space (instead of pixel space), every overlay is wrong. Validate early with one fixture; tune the prompt; pin the contract.
- **OCR vs VLM split.** It is tempting to OCR first and then pass text to a normal LLM. Don't — the VLM's own bbox grounding is the load-bearing feature for the citation contract. OCR is a fallback only when the VLM fails.
- **Cohere account dependency.** If the Cohere account doesn't have rerank credit when the demo runs, evidence retrieval falls over. Mitigation: a no-rerank fallback that takes top-3 from the dense leg; eval suite includes a case that validates the fallback path.
- **W1 surface drift.** While building W2, the W1 graph keeps running. Every change to `verifier.ts`, `types.ts`, or the snapshot shape must keep W1 evals green. The contract tests in `agent/tests/auth/` and `agent/tests/snapshot/` are the early-warning system.
- **Eval cost.** A 50-case nightly experiment that hits the real vision LLM is non-trivial. Recommendation: nightly experiment runs only on `master` after merge, not on every PR; per-MR layer stays stubbed.
