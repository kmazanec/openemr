Clinical Co-Pilot Architecture

A read-only, source-cited clinical briefing agent for the 90-second pre-visit window. Built as an OpenEMR-native feature with a private LangGraph runtime.

90s Core moment: the physician is between rooms and needs context fast.
5-15 MVP concurrency: a family-practice sized clinical team.
5 Tool families: patient context, labs, meds, encounters, schedule.
0 Write actions: no orders, notes, prescriptions, or chart updates in v1.

Architecture lens

Principles That Constrain The Design

The architecture starts from the user and safety constraints defined during presearch, then maps them onto OpenEMR's existing boundaries.

User problem

Dr. Patel needs a glanceable briefing before entering the room: who the patient is, why they are here, what changed, current meds, allergies, labs, and recent encounters.

Default briefing Follow-up drill-down Patient-bound context

Why this scope

Presearch rejected broader hospitalist or ED workflows because the primary-care scheduled day is more predictable, easier to defend, and maps cleanly to a small tool surface.

System of record

OpenEMR remains clinical truth. The agent reads, summarizes, and cites; it does not create independent clinical state.

Human in the loop

The clinician always decides. The agent advises, flags, and retrieves; it does not prescribe or act.

Proof over polish

Every clinical claim needs a source reference. Unverified content is stripped before display.

System shape

Two Bounded Contexts

OpenEMR owns the clinical boundary. The private LangGraph service owns agent orchestration.

01 Browser UI

OpenEMR-origin panel with briefing, citations, follow-ups, streaming state.

02 Agent Module

Custom PHP module for routes, policy gates, snapshots, audit, proxying.

03 Adapters

Typed chart reads, normalization, source references, PHI minimization.

04 LangGraph

Self-hosted Node service running graph nodes and LLM calls.

05 Verification

Claim ledger, deterministic checks, safety rules, response gate.

06 State + Traces

Postgres stores state; LangSmith records metadata, not PHI bodies.

Why split PHP and Node

OpenEMR is PHP and owns auth/data. LangGraph.js is the chosen agent framework. Splitting services keeps OpenEMR stable while letting the agent runtime evolve independently.

Why private service

The browser never talks directly to the agent, avoiding CORS, separate login, browser-held agent tokens, and a second public attack surface.

OpenEMR boundary

Integrate As A Custom Module

The agent enters OpenEMR through the module system, explicit route/listener registration, and patient or schedule UI entry points.

UI entry points

Patient-chart button, schedule annotation, inline panel, or module-hosted launch page.

HTTP route

Register agent routes through OpenEMR REST extension events where possible.

Policy services

Validate session, site, patient, scope, data category, and use case.

Proxy bridge

Forward minimized requests to the private service and stream responses back.

Decision criteria from presearch

Stack choice should fit OpenEMR, minimize core patches, and support the 90-second workflow. The user should experience this as an OpenEMR feature that happens to use AI, not as a separate app.

Request lifecycle

Default Briefing Flow

A briefing is context-triggered: opening a patient or schedule context starts the workflow without a typed prompt.

Open Patient context

Clinician opens a chart or schedule item inside OpenEMR.

Gate Auth + policy

OpenEMR verifies session, site, patient, scope, and read-only task.

Audit Disclosure event

AGENT_PHI_DISCLOSURE is emitted before model-bound data leaves OpenEMR.

Shape ChartSnapshot

Adapters normalize data and remove unnecessary identifiers.

Run LangGraph

Graph synthesizes, verifies, formats, and records metadata.

Show Cited response

OpenEMR streams verified briefing and citations to the browser.

Latency target

Presearch target was 3-7 seconds with a loading state. The integrated MVP uses 5-8s P50 and 30s hard ceiling because OpenEMR bootstrap and LLM calls are synchronous costs.

Silent omission

Missing allergies or meds cannot be hidden. The response must show a safety-critical gap instead of producing a clean but unsafe summary.

Model input boundary

ChartSnapshot, Not Raw Chart

The LLM gets a minimized clinical snapshot with source references, not raw SQL rows or broad FHIR bundles.

Included in the snapshot

Data Presentation requirement
Appointment context Why the patient is here today.
Display-safe demographics Enough identity to orient the clinician.
Current medications Names, dosages, recent changes, source record.
Recent labs Value, date, unit, reference range, abnormal flag.
Allergies Always surfaced when present.
Recent encounters Date, type, reason, source-backed summary.

Excluded by default

  • SSN and driver's license
  • Full address and unrelated contact data
  • Billing-only fields
  • Non-unique MRN/pubpid as identity
  • Full chart history outside the requested window

Why adapters exist

Presearch wanted FHIR/API tools to avoid direct SQL. The audit adds a stricter criterion: data must also be normalized and minimized before it becomes model input.

Legacy data hazards

OpenEMR can contain duplicate pubpid, zero-date sentinels, unbounded strings, and fragmented form_* data. The adapter layer absorbs those hazards.

Agent runtime

Small Deterministic LangGraph

LangGraph.js gives explicit graph state and node-level traceability without building a sprawling multi-agent system.

Node LoadState

Load patient-bound conversation state from Postgres.

Node PlanContext

Classify default briefing vs. follow-up and needed categories.

Node Retrieve

Use snapshot facts or request additional minimized context.

Node Synthesize

Create draft response and structured claim ledger.

Node Verify

Check source support and hard clinical rules.

Node Format

Stream cited briefing with explicit gaps.

Framework decision

LangGraph was chosen over a custom loop because explicit nodes and state transitions make the clinical workflow auditable and easier to defend.

Model decision

Claude Sonnet 4 is used for retrieval and verification in the MVP for tool use, context window, and instruction-following. Cheaper verifier models wait for eval proof.

Trust layer

Verification Before Display

The response users see is not the first model draft. It is the post-verification answer.

1

Claim ledger

Every factual claim is represented as structured data with category, source, safety flag, and status.

2

Deterministic checks

Structured facts like dose, lab value, date, allergy, and patient identity are checked directly.

3

Gate output

Unsupported claims are stripped; malformed output is rejected; safety-critical gaps are displayed.

Why source tags at retrieval time

Presearch rejected post-hoc fact tracing because reverse-mapping prose back to records is slower and less reliable than producing citations as part of retrieval.

Clinical hard stops

Allergies, drug interactions, and dosage-sensitive warnings cannot be probabilistic labels. They are verified or the system fails closed.

Trust boundaries

Security Model

The agent has no public identity and no privileges beyond authorized OpenEMR chart context.

Browser → OpenEMR

Standard OpenEMR session. No second login. No agent tokens in the browser.

OpenEMR → Agent

Private request envelope over Railway private network. Optional shared secret or mTLS for production.

Agent → LLM

Provider API key lives server-side. Model receives minimized snapshot, not full chart.

Authorization criteria

Multi-user clinical settings are the norm. The policy gate checks site, patient, scope, data category, and supported task before disclosure.

Prompt injection

Patient notes are untrusted input. Instructions inside chart text are ignored and cannot create verified claims without source support.

Compliance posture

Audit And PHI Controls

Demo data is used, but the architecture treats chart content as PHI-equivalent.

AGENT_PHI_DISCLOSURE

Emitted before model-bound chart content leaves OpenEMR. It records user, site, patient identifiers, request/conversation ID, purpose, disclosed categories, destination, timestamp, and result status when known.

It does not store raw prompt or completion text.

Production requirements

  • Signed BAA with model provider
  • No-training/no-retention settings
  • TLS 1.2+ outbound calls
  • Retention policy
  • Centralized audit monitoring
  • Breach response procedures

Why explicit audit

Presearch required audit/compliance from day one. The architecture therefore uses a dedicated disclosure event rather than relying only on configurable query or API logs.

Quality system

Evals, Observability, And Cost

The agent is only trustworthy if failures are measurable and regressions are caught.

LangSmith

Graph/LLM traces with latency, token, cost, tool, and status metadata. No PHI bodies.

Vitest evals

Happy path, failure path, adversarial cases, and schema-drift smoke tests.

Cost tracking

Per-request token/cost metrics plus usage model for 100, 1K, 10K, and 100K users.

Eval criteria

Tests must cover correctness, all claims source-attributed, no cross-patient leakage, prompt-injection resistance, and graceful failure on missing data.

Cost criteria

Cost projection is not cost-per-token times users. It depends on patients per clinician, follow-up rate, snapshot size, cache hit rate, retention, and audit volume.

Operations

Railway Deployment

A pragmatic deployment for the sprint: simple enough to ship, structured enough to defend.

Resource Visibility Purpose
OpenEMR service Public EHR UI, auth, agent module, browser-origin proxy.
LangGraph service Private Self-hosted Node/TypeScript agent runtime.
MySQL Private OpenEMR database.
Postgres Private Agent state, claim ledgers, metadata, costs.
Object storage Private/public by config OpenEMR documents.

Why Railway

Presearch prioritized simple infra over DevOps complexity. Railway gives managed MySQL, Postgres, object storage, variables, environments, and deploys in one place.

Why Postgres for agent state

LangGraph has first-party Postgres checkpointing, and separate storage reduces the blast radius if the agent service is compromised.

Production thinking

Scale And Performance

The MVP targets a family practice, while documenting the changes needed for a 500-bed hospital.

MVP target

  • 5-15 concurrent users
  • 5-8s P50 response
  • 30s hard ceiling
  • SSE streaming

Hospital changes

  • Streaming outside PHP-FPM
  • Background precomputation
  • Application cache
  • Rate limits

Data operations

  • Retention jobs
  • Audit export
  • Operational indexes
  • Anomaly detection

Scale criteria

We are not building for hospital scale in week one, but we avoid choices that foreclose it: private service boundary, separate state store, explicit audit, and eval-driven model changes.

Tradeoffs

Rejected Alternatives

These options were simpler in one dimension but weaker against the clinical, security, or maintainability criteria.

Direct Node-to-MySQL reads

Rejected because it bypasses OpenEMR authorization and audit and exposes the agent to legacy schema hazards.

Raw FHIR bundle prompting

Rejected as model input because raw bundles are too broad and PHI-heavy. FHIR remains useful inside adapters.

Standalone public SPA

Rejected because it creates a second origin, token handling, and worse workflow fit.

Third-party SMART app flow

Rejected for MVP because this is an internal OpenEMR feature, not a cross-EHR marketplace app.

Self-hosted open-weight LLM

Rejected for MVP because GPU/model operations add too much delivery risk for the sprint.

Defense summary

The chosen architecture is intentionally narrow: OpenEMR-native, read-only, source-cited, minimized, audited, eval-gated, and deployable in the project timeline.
