Start with the user

Dr. Patel And The 90-Second Window

Every architectural choice in this deck traces back to one person and one moment. Pick the wrong user and the rest is wasted.

The user

Dr. Patel is a family medicine physician at a 12-physician group. 20-patient day, 8:00 AM to 5:30 PM, lunch eaten at her desk. About a third of her panel is partner coverage — patients she has never met, scheduled with her because a colleague is out.

She is not anti-tech. She knows OpenEMR well enough to find what she needs eventually. "Eventually" is what she does not have between rooms.

The moment

The 30 seconds before she opens an exam-room door, she is finishing the previous patient's note and walking down a hallway. She has maybe 90 seconds to learn who this person is, why they are here, what changed, what they take, what to be careful of.

Today the EHR forces four or five screens. This is the problem.

Why this user, not a hospitalist or ED resident

The primary-care scheduled day is predictable, has a clean read-only surface, and maps to a small tool set. ED intake and hospital rounding have higher write-action pressure and more ambient context — wrong shape for an MVP.

Why an agent, not a better dashboard

What matters varies per patient. A dashboard prioritizes the same fields every time and pushes prioritization onto the physician. An agent reads the actual record and surfaces what is notable for this patient. Drill-down questions are unpredictable; conversation handles them, a static UI cannot.

Concrete scenarios

Five Use Cases That Define The Build

UC1 is the entry point. UC2-UC4 are the three shapes of one-tap follow-up the agent auto-suggests from the briefing — each pulling from a different data category. UC5 is the same engine applied to her morning schedule.

UC1 — Default pre-visit briefing

Dr. Patel taps a patient's name. Without typing, she sees: "Maya Patel, 67, diabetes follow-up. Since last visit (4mo): A1c 8.2 (was 7.4), started lisinopril 6 weeks ago. Current meds: metformin 1000 BID, lisinopril 10 daily. Allergic to penicillin." Eight seconds, then she walks in.

The briefing always includes deltas since last visit, current meds, allergies, and today's reason for visit. Below it, the agent generates 3-5 contextual one-tap follow-ups drawn from what is actually in the record.

Why an agent: the briefing is prioritized for this patient. Zero input required — she is opening a chart, not starting a chat.

UC2 — Lab/vitals trend follow-up

The briefing shows A1c moved 7.4 → 8.2. The agent suggests "Why is the A1c up?" She taps. The agent returns the trend, related labs, and any encounter notes that bear on the change.

Why an agent: the suggestion only appears because the value moved. A static lab-trend widget cannot read the surrounding notes.

Data source: procedure_result (lab values), encounter notes.

UC3 — Medication change follow-up

The briefing flags lisinopril as a new medication. The agent suggests "When was lisinopril started, and why?" She taps. She gets the prescribing date, the prescribing partner, the documented indication, and the starting dose.

Why an agent: medication histories are scattered across prescriptions, encounter notes, and provider documentation. The agent reads across them.

Data source: prescriptions, lists (medication problem list), encounter notes.

UC4 — Recent outside care follow-up

The agent notices an imported CCDA on file and suggests "Has she had care at other facilities recently?" She taps. The agent surfaces a recent ED visit and cardiology consult parsed from imported CCDAs.

Why an agent: external care is buried under the documents tab, easy to miss. The agent surfaces it only when it is recent and relevant.

Data source: external_encounters, external_procedures, ccda table.

UC5 — Schedule-aware morning prep

At 7:50 AM, briefings are pre-computed for today's list. Patients with notable items — new abnormal labs, recent ED visits, new meds — are flagged in the schedule view. She glances down and mentally flags the three patients needing extra attention today.

Why an agent: "notable" is patient-specific and clinically judged — depends on the patient's baseline. A "patients with new labs" filter is too coarse.

System shape

Architecture At A Glance

Two bounded contexts. OpenEMR owns the clinical boundary; a private LangGraph service owns agent orchestration. The browser only ever talks to OpenEMR.

System of record

OpenEMR stays clinical truth. The agent reads, summarizes, and cites — it does not create independent state.

Human in the loop

Read-only in v1. The agent prepares; the physician decides. No orders, no notes, no prescriptions.

Proof over polish

Every clinical claim carries a source reference. Unverified content is stripped before display.

Data Why it is in scope

Excluded by default

  • SSN and driver's license
  • Full address and unrelated contact data
  • Billing-only fields
  • Non-unique MRN/pubpid as identity
  • Full chart history outside the requested window

Why a snapshot, not raw FHIR or SQL

Raw FHIR bundles are PHI-heavy and broad. Direct SQL bypasses OpenEMR auth and audit. The snapshot is the boundary that lets the agent be useful without exporting the chart. Source references travel with the data, so verification has something to check against.

Agent runtime and trust layer

LangGraph Plus Verification Gate

A small, deterministic graph in LangGraph.js. The response the user sees is the post-verification answer, not the first model draft.

Source-support and clinical hard-stops.

Node Format

Stream cited briefing, with explicit gaps where data is missing.

1

Claim ledger

Every factual claim is structured: category, source ref, safety flag, status. Citations are produced at retrieval time, not reverse-mapped after.

2

Deterministic checks

Doses, lab values, dates, allergies, and patient identity are verified against the snapshot directly — not re-prompted to a model.

3

Gate output

Unsupported claims stripped; malformed output rejected; safety-critical gaps surfaced rather than hidden behind clean prose.

Why LangGraph over a custom loop

Explicit nodes and state transitions make the clinical workflow auditable. A free-form loop would be smaller code but harder to defend in a clinical context.

Why Claude Sonnet 4

Tool use, context window, and instruction-following good enough for both retrieval and verification roles in the MVP. Cheaper verifier models wait for eval proof before being adopted.

What was actually hard

Hardest Problems And How We Solved Them

The interesting work was not "call an LLM." It was making the LLM safe and useful inside a 25-year-old clinical codebase without forking it.

1. Integrate into a legacy PHP monolith without forking it

OpenEMR is a long-lived codebase with global state, two template engines, and an upstream we want to stay mergeable with. Bolting Node services into core, patching kernel routes, or grafting a parallel auth model would all "work" and all be unshippable.

Solution: a custom module — the existing extension point. No core patches. Routes and listeners registered through the module's bootstrap. UI entry points hook into the patient and schedule views the way other modules already do. The result is a feature that follows the same shape as the rest of OpenEMR's extensions and could plausibly be proposed upstream as one.

2. PHP and Node, without bolting Node into PHP

LangGraph.js is the right framework. OpenEMR is PHP. Embedding a Node runtime inside PHP-FPM is the wrong shape.

Solution: private-network split. The PHP module proxies a minimized request to the Node service over Railway's private network. Both stacks stay idiomatic; the browser only ever talks to OpenEMR.

3. Silent omission of safety-critical data

A clean summary that quietly drops an allergy is worse than no summary. This is the failure mode that ends pilots.

Solution: claim ledger plus deterministic checks at the verification gate. Allergies and interactions are not probabilistic — they are verified, or the system fails closed and renders the gap.

4. Prompt injection from chart text

Patient notes are untrusted input. A previous provider's free-text note can contain "ignore previous instructions" or worse.

Solution: verification is structural, not instruction-following. Instructions embedded in chart text cannot create verified claims without source support, because the gate checks structured records, not the model's narrative.

5. Legacy schema hazards

Duplicate pubpid, zero-date sentinels, unbounded strings, fragmented form_* tables. Anything that hands raw rows to a model produces wrong answers confidently.

Solution: the ChartSnapshot adapter layer absorbs these hazards. Normalization, identifier discipline, and missingness handling all happen before the model sees anything.

Tradeoffs

Key Decisions And Rejected Alternatives

Each row: the choice, the option we did not take, and why.

Choice Rejected alternative Why
Custom OpenEMR module Standalone public SPA / SMART app SPA creates a second origin, token handling, and worse workflow fit. SMART is for cross-EHR marketplace apps; this is an internal feature.
Private LangGraph service Browser → agent direct, or Node embedded in PHP Avoids CORS, second login, browser-held agent tokens, and a second public attack surface. Keeps PHP and Node idiomatic.
ChartSnapshot adapters Direct Node-to-MySQL or raw FHIR bundle prompting Direct SQL bypasses auth and audit. Raw FHIR is broad and PHI-heavy. The snapshot is the contract; FHIR can live inside adapters.
LangGraph.js Custom agent loop Explicit nodes and state transitions make the clinical workflow auditable and easier to defend.
Claude Sonnet 4 (managed) Self-hosted open-weight model GPU and model operations add too much delivery risk for the sprint. Managed API with BAA fits the timeline.
Postgres for agent state Reuse OpenEMR MySQL LangGraph has first-party Postgres checkpointing. Separate storage reduces blast radius if the agent service is compromised.
Read-only in v1 Write-back to chart Write actions multiply review surface and clinical risk. Read-only proves the briefing loop first; write-back is the planned next step.

Defense summary

The architecture is intentionally narrow: OpenEMR-native, read-only, source-cited, minimized, audited, eval-gated, and deployable in the sprint timeline. One consideration that shaped several of these choices — though not a primary design goal — is that an integration shaped like other OpenEMR modules is more plausibly adoptable upstream than a forked or sidecar approach would be.

Security, audit, operations

Boundaries, Audit, And Deployment

Demo data today, but the architecture treats chart content as PHI-equivalent and the deployment shape carries forward into production.

Browser → OpenEMR

Standard OpenEMR session. No second login. No agent tokens in the browser.

OpenEMR → Agent

Private request envelope over Railway private network. Shared secret or mTLS for production.

Agent → LLM

Provider API key server-side. Model receives minimized snapshot, not full chart.

AGENT_PHI_DISCLOSURE audit event

Emitted before any model-bound chart content leaves OpenEMR. Records user, site, patient identifiers, request and conversation ID, purpose, disclosed categories, destination, timestamp, and result status. Does not store raw prompt or completion text.

Dedicated event, not buried in generic API logs — chosen so audit/compliance review can trace every disclosure without query-log archaeology.

Production checklist

  • Signed BAA with model provider
  • No-training / no-retention settings
  • TLS 1.2+ outbound
  • Retention and breach response policies
  • Centralized audit monitoring
