Multimodal Evidence Agent — Week 2 demo

The Co-Pilot Sees, Routes, And Cites

A primary care physician opens a patient's chart and asks the co-pilot a question. The co-pilot reads structured chart data, the messy lab PDF the front desk just uploaded, and the relevant published guideline — and answers with every claim grounded in a source the clinician can click on.

Margaret Chen 58-year-old patient with type 2 diabetes and hyperlipidemia. Today's chart is open and ready.
3 Source types in one citation shape — chart record, extracted document, published guideline.
108 USPSTF recommendations indexed in the guideline corpus — hybrid retrieval, reranked before reaching the answer model.
0 Auto-writes to the chart. Every derived fact is gated on explicit clinician review.

The Front Desk Just Dropped Off A Lab

With Margaret's chart open, drag the scanned lab PDF onto the conversation panel. The agent has never seen these contents — the front desk just uploaded the bytes.

Action

Drag chen-lab-results.pdf onto the paperclip area in the conversation panel.

What you'll see

  • Upload progress indicator, then a "Extracting document…" status line in the conversation thread.
  • Live SSE progress as the pipeline moves through each stage — rasterize, vision, validate, match, persist.
  • When the pipeline exits, the status line clears and the document is ready to be referenced.
Strict schema Per-field bbox Pending confirmation

What's happening underneath

  • Rasterize — PDF split into page images, uploaded to short-TTL storage.
  • Vision — vision-capable LLM reads pages with a strict extraction schema. Each field carries a page, bounding box, verbatim quote, and self-reported confidence.
  • Validate — Zod parse with strict mode. Missing required fields fail; unknown fields drop.
  • Match — extracted demographics compared against the chart.
  • Persist — structured extraction lands at pending confirmation. The chart is not modified.

The Lab Is Now A First-Class Source

With the extraction complete, ask the agent what changed. Every claim in the answer points back to a region of a specific page on the document.

Copy & paste into the chat

What did this lab show that I should pay attention to, and is anything outside the reference range?

What you'll see

The answer renders below the chat with a From documents section. Each claim has a chip — hover one and the tooltip shows the page number and the document identifier. Every numeric value the answer mentions traces back to a region the vision model bounded on a specific page of the upload.

The agent is reading a scanned PDF it has never seen before, extracting structured data with a strict schema, and citing every claim back to a region on a specific page. Malformed extractions never reach the answer.

Demo step 3 Ask for guideline-grounded evidence

Now Pull In Published Guidance

No upload required. The agent decides on its own when to retrieve from the chart, when to retrieve from the guideline corpus, and when to answer directly. Routing decisions are logged and inspectable.

Copy & paste into the chat

Should Margaret be on aspirin for cardiovascular disease prevention given her diabetes and hyperlipidemia?

What you'll see

The answer renders in two sections:

  • What's in the chart — her age, lipid panel, current statin, ASCVD risk factors. Each chip clicks through to the OpenEMR record.
  • Evidence — the relevant USPSTF aspirin recommendation. Each chip's tooltip shows publication, year, and section.

No From documents section appears, because no document was relevant to this question. Empty sections are omitted by design.

Why this is the marquee question

The agent didn't retrieve a guideline because that was hardcoded. It retrieved because the LLM supervisor reasoned about the question and chose to. The routing log shows closed-enum tool choice, written rationale per decision, capped iteration count. The agent can't invent a tool, and it can't loop forever.

Demo step 4 Combine the lab, the chart, and a guideline

All Three Source Types In One Answer

With the lab from step 1 already extracted and the question style from step 3, ask something that needs all three. This is the case where the architectural choices pay off.

Copy & paste into the chat

Given the new A1c result from this lab, does USPSTF recommend any change to her screening or preventive medications?

What you'll see

The supervisor fans out: chart for current preventive medications, extracted document for the new A1c value the agent just learned about, guideline for the USPSTF recommendation. The answer renders all three sections with chips that behave differently per source type:

chart Click → opens the OpenEMR record page in a new tab.
extracted_document Hover → page number and document identifier. Every claim is anchored to a region the vision model bounding-boxed.
guideline Hover → publication, year, and section. The verifier confirms every quote substring matches the indexed chunk.

Three source types, one citation shape under the hood. The verifier indexes all three uniformly — every claim either resolves to a specific source or it gets dropped before the answer reaches the screen.

Demo step 6 — safety guardrail Wrong-patient document

The Pipeline Refuses Mismatched Demographics

Most demos show the happy path. The interesting demos show what the system refuses. Wrong-patient-into-the-wrong-chart is the harm scenario this product has to avoid — the agent stops it cold before any persistence.

Action

Open a different patient's chart, then drop Margaret's lab PDF onto the panel.

What you'll see

The pipeline runs through extraction and validation, then the patient-match node compares the demographics on the document against the chart. They don't match. The pipeline halts with a typed refusal — the chart is never modified, no facts are written, and the panel surfaces a clear "this document does not appear to belong to this patient" error.

The match is structural and runs before any persistence. Even if the extraction were perfect, mismatched demographics stop the pipeline cold.

The Supervisor Knows When Not To Do Work

The supervisor is allowed to refuse. When the question has nothing to do with the patient's care, no tools are invoked, no tokens are spent, and the trace shows a single iteration with the rationale recorded.

Copy & paste into the chat

What's the weather in Austin today?

What you'll see

The supervisor recognizes on the first iteration that no clinical tool applies. It routes directly to a refusal — no chart fan-out, no guideline retrieval. The trace shows a single supervisor iteration with the rationale recorded.

This is one of the rubrics the eval suite specifically pins so it can't regress quietly — safe_refusal is asserted on every change.

Recap — the system at a glance

What Just Happened, Across The Whole Stack

Seven steps, four capabilities — multimodal ingestion with provenance, hybrid retrieval over a curated guideline corpus, an inspectable LLM supervisor making tool-call decisions, and a verifier that drops any claim it can't anchor to a specific source. The next slide shows where each of these lives.

Multimodal ingestion with provenance

A separate ingestion pipeline reads scanned PDFs and intake forms with a strict-schema vision LLM. Every extracted field carries a page, a bounding box, a verbatim quote, and a self-reported confidence. Wrong-patient documents are refused before persistence; the chart is never auto-modified.

Hybrid evidence retrieval

Every published USPSTF recommendation is parsed deterministically into per-section chunks, embedded, and indexed with both dense and sparse vectors. Retrieval fuses both legs to a top-20 candidate set, then reranks to top-3 with a purpose-built reranker. Top-3, not top-20, reaches the answer model.

Inspectable LLM supervisor

The supervisor is an LLM, not a rule set — but it can only choose from a closed set of tool calls and is required to write a rationale for every decision. The iteration count is capped. Every iteration logs to LangSmith with state observed, chosen tool, rationale, args, and token usage.

Verifier as the final gate

Every claim in every answer must resolve against the indexed source set for its source_type — chart record, document page+bbox, or guideline chunk+quote. Claims that don't resolve are dropped before the answer reaches the screen. There is no fallback path that lets unsourced text through.

Eval-driven CI — what covers this demo today

Two layers run on every change: a deterministic Vitest gate against stubbed vendors, and a nightly LangSmith experiment against the real model — vision, supervisor, embeddings, reranker. Rubrics are boolean (schema_valid, citation_present, factually_consistent, safe_refusal, no_phi_in_logs); failures are actionable; CI blocks merges that regress them.

Why two graphs, not one

Producer-shaped work (ingest a document) and consumer-shaped work (answer a question) have different latency, failure, and cost profiles. Forcing them into one runtime collides their concerns. The same ingestion pipeline runs whether it's triggered by a panel upload, a front-desk autosweep listener, or a command-line replay.

Why the supervisor is an LLM

Routing by hand-written rules is defensible but doesn't exercise agentic reasoning. Constrained LLM routing — closed-enum handoffs, required rationale, capped iteration count, full LangSmith logging — produces stronger inspectability. The model is explaining itself per decision, and the explanation is logged.

Why one citation shape

The verifier resolves every claim against an indexed source set — same accept-or-reject boundary regardless of source type. The renderer dispatches on source_type for chip behavior. One shape keeps verification and UI symmetric; a discriminated union of three shapes would force a switch on every path.
